10Products

10.1 Point cloud

07_results/dense.las is a LAS 1.2 file with point format 2 (XYZ, RGB, classification), 0.1 mm coordinate resolution. Above 4,294,967,295 points it becomes LAS 1.4 automatically. When the run is georeferenced, the LAS carries the coordinate system (and the height system, Section 8.2). dense.ply has the same points with double-precision coordinates; --ply off skips it to save disk and time.

--tiled-las-output SIZE writes square LAS tiles of SIZE metres to 07_results/dense_tiles/ with a tiles.csv index instead of one large file. --voxel SIZE thins the cloud to one point per voxel.

07_results/point-confidence.bin stores, for every point in cloud order, its supporting cameras, views, evidence score and more (--point-confidence off skips it). --export-confidence RUN converts it to CSV.

10.2 Per-point values and uncertainty

--point-attributes LIST chooses which values each point carries, as LAS Extra Bytes and PLY properties:

ValueMeaning
surface (default)Group: surface normal, roughness, surface variation, planarity and normal diagnostics.
noneXYZ and RGB only (smallest files).
viewsNumber of cameras confirming the point.
angleLargest triangulation angle, degrees.
confidenceEvidence score 0..1 (a ranking, not a probability).
sourceThe camera that produced the point, in the LAS Point Source ID.
depth_spreadStandard deviation of the averaged cameras' depths (3+ cameras).
height_sigma, ray_sigmaCalibrated 1-sigma precision vertically and along the viewing ray, in metres (group uncertainty).
allEverything.

The sigmas come from the images only. The fusion model's precision estimate for each point is scaled by a factor measured in the run itself, from how much the depths of different cameras scatter where they were averaged. They describe local precision (noise and disagreement between cameras); errors of the camera orientations and of the georeferencing are not included. The calibration factor and distribution are in report.txt and 07_results/point-uncertainty.json. The uncertainty values need image fusion.

Examples: per-point values
# Surface attributes plus views and calibrated sigmas
photogrammetry -i IMAGES -o PROJECT --preset drone,forest --point-attributes surface,views,uncertainty

# Smallest files: XYZ and RGB only, 1 km LAS tiles
photogrammetry -i IMAGES -o PROJECT --point-attributes none --tiled-las-output 1000

10.3 Surface model (DSM)

Every georeferenced run gets dsm.tif: the highest point per cell (--report-dsm-statistic mean for the mean), as a Float32 GeoTIFF with NaN for empty cells, plus a world file, a preview and a JSON description. The cell size is chosen automatically within --report-dsm-max-dimension (1024 cells per side) or set with --report-dsm-resolution. No gaps are filled.

Example: a 0.25 m DSM of a finished run, without reprocessing
photogrammetry --export-report PROJECT/runs/RUN_ID --report-dsm-resolution 0.25 --report-dsm-max-dimension 4096

10.4 Ground, terrain and canopy height

--classify-ground classifies the ground in the final cloud and writes the terrain model. It needs georeferenced output and uses no external terrain data. The method is a progressive morphological filter on the lowest points, limited by the camera rays (terrain cannot stand above a ray that reached its point) and by a slope envelope, with automatic tolerances from the cloud. Under closed canopy, patches of crown tops that the filter would take for ground are recognised and rejected.

Results in 07_results:

  • LAS classes in dense.las: 2 ground, 7 low noise, 1 other.
  • dtm.tif: terrain; chm.tif: canopy height (highest point minus terrain).
  • ground_support.tif: 1 observed ground, 2 interpolated, 3 blocks camera rays; ground_uncertainty.tif: half the difference between terrains from two halves of the data.
  • ground.json with the settings and checks.

Settings: --ground-cell (auto: 3 × point spacing, 0.25–2 m), --ground-max-slope (35°), --ground-max-object (30 m, the largest non-ground object). Under closed canopy the terrain is interpolated from the nearest visible ground; ground_support.tif shows where.

10.5 Orthomosaic

--orthomosaic writes 07_results/orthomosaic.tif at the end of the run: the original photographs at full resolution projected onto the surface of the cloud, as a tiled RGBA GeoTIFF (BigTIFF when large) with a world file and a JSON description. --export-orthomosaic RUN makes one for a finished run without reprocessing.

--orthomosaic-modeResult
true (default)True orthomosaic: every pixel from a camera that sees it, so buildings and trees do not lean. Transparent where nothing is known.
classicConventional orthophoto without holes: the surface is smoothed and filled, each pixel comes from the camera nearest its image centre, seams are feathered. Tall objects lean.

Pixel size: --orthomosaic-resolution (auto: the median ground sample distance). Other options control the surface cell, gap filling, strict visibility and, for classic mode, smoothing and feathering. The orthomosaic needs a projected coordinate system, and the photographs must still be where the run found them.

Examples: orthomosaic
# With the run
photogrammetry -i IMAGES -o PROJECT --orthomosaic

# Classic mode, 5 cm pixels, for a finished run
photogrammetry --export-orthomosaic PROJECT/runs/RUN_ID \
  --orthomosaic-mode classic --orthomosaic-resolution 0.05

10.6 Processing report

07_results/processing-report.pdf documents the run: summary and quality flags, survey data (images, flying height, ground resolution, area, tie points, reprojection error), camera calibration, camera locations and their errors, ground control and check points, lidar reference, elevation models and processing parameters. --report-detail full adds detailed diagnostics (solver profiles, resources, OpenCL, all settings). --report html writes HTML instead; a JSON companion keeps every number. --export-report RUN regenerates the report of a finished run.

10.7 Camera orientations

The final calibration and camera poses are in 04_geometry/final/ and PROJECT/cameras.csv. To use them in other software, export them during the run with --orientation-output-format LIST or afterwards:

photogrammetry --export-orientations RUN --orientation-output-format csv,colmap,metashape

Formats: csv, csv-opk, native, colmap, bundler, openmvg, opensfm, metashape, micmac, opencv, inpho. --orientation-pixels processed exports the undistorted dense images' intrinsics instead of the original photographs'.

11Performance, memory and large projects

11.1 Memory

--memory-mb N is the processing budget in MiB, not a total RAM limit. The program restarts itself with a Java heap of about N/0.65 (for example 56000 gives an 84 GB heap); native memory for images, feature extraction and GPU buffers comes on top. A safe starting point is half the RAM; the window uses that by default.

--ram-limit-mb N is the total RAM ceiling POSE plans for (0 = detect the computer's or job's limit). It caps the heap and throttles parallel feature extraction and matching. Neither option is enforced by the operating system; use the scheduler's limit for that.

--estimate-memory prints the plan without processing. Other budgets: --image-memory-mb (decoded images), --descriptor-memory-mb, --surface-memory-mb, --fusion-cache-mb; the defaults are derived from --memory-mb.

On clusters. The resident memory reported by the system includes memory-mapped depth maps, which the operating system can drop at any time. A warning that host RAM is nearly exhausted is therefore not necessarily a problem; a job killed by the scheduler is.

11.2 GPU

The GPU runs dense matching, depth fusion, the orthomosaic and some filters. --gpu-memory-mb limits the GPU working set (default 70% of the card, at most 95%). Fusion on the GPU needs double precision; without it fusion runs on the CPU. --fusion-gpu-normals on also computes normals on the GPU (faster, not bit-identical to the CPU). If the GPU runs out of memory, POSE falls back to smaller batches, streaming or the CPU; the fallbacks are listed in 06_fusion/backend.json.

11.3 Speed

  • Resolution is the main factor: each step down in --quality divides the dense work by about four.
  • --cores sets the CPU threads (default half the processors).
  • --mvsgm-cameras-in-flight auto computes several cameras' depth maps at once; --stereo-pairs-in-flight does the same for pair SGM. Results are identical to serial processing.
  • --descriptor-matcher flann speeds up matching of large sets; --calibration-trial-method subset or joint speeds up lens refinement of large blocks.
  • --step 2 halves the points per image side and speeds up fusion; --ply off and --point-confidence off save output time.

11.4 Disk

Depth maps and fusion data are kept on disk in the run folder while the dense step runs and removed after it. Decoded photographs are cached in the run (--processed-image-cache) while enough disk is free. Dense checkpoints keep up to one interval's depth maps. Plan for tens to hundreds of gigabytes for large blocks at high resolution. --storage minimal keeps the fewest intermediate files; --diagnostics keeps everything for inspection.

11.5 Large image sets

For thousands of photographs:

  • Use --pair-selection auto with GPS, --descriptor-matcher flann and --calibration-trial-method subset.
  • Keep --registration-bundle-growth on to limit drift; consider --registration-pose-check on.
  • Use mvsgm with dense checkpoints, so an interrupted dense step can resume.
  • --block-processing auto|on splits the images into overlapping blocks by GPS position, processes them one after another and merges the results into PROJECT/merged/dense.las. Rerunning the same command resumes after an interruption.
  • --tiled-las-output keeps the output files manageable.

12Checking quality

Report and quality flags

Start with the summary page of the processing report. Quality flags point out problems: images that were not aligned, high reprojection errors, cameras flagged by screening, weak lens fits, GPS residuals, little observed ground, lidar parameters that could not be determined. The same flags are on the Project tab.

Accuracy

  • Reprojection error (pixels) measures how well the cameras and tie points fit together; typical values are a fraction of a pixel. It does not measure absolute accuracy.
  • GPS residuals show how well the block fits the image GPS; for consumer GNSS a few metres is normal.
  • Check points are the only independent measure of absolute accuracy. Use type=check GCPs or --gcp-check auto.
  • Lidar reference gives the distances of the tie points to the lidar surface and maps of the remaining differences.
  • Per-point uncertainty (--point-attributes uncertainty) maps local precision across the cloud.

Visual checks

  • In the 3D view, look for doubled surfaces, misplaced cameras (red pyramids) and noise above or below the surface.
  • On the Map tab of the Images window, lower the opacity: misaligned photographs appear doubled.
  • --analyze-run RUN measures local surface thickness and offsets in the cloud without changing it.

14Worked examples

Each example is a complete command sequence for a common kind of survey. Commands are shown for Linux and the Windows command prompt alike; on Windows use photogrammetry.bat and replace the line continuation \ with ^ (or write the command on one line). Paths are examples.

14.1 Drone survey of a forest stand

A consumer drone (no RTK), 30–300 photographs with 80% overlap, terrain and canopy height wanted.

photogrammetry -i /data/stand12/images -o /data/stand12/project \
  --preset drone,forest --quality high \
  --classify-ground --orthomosaic \
  --point-attributes surface,views,uncertainty

What to check afterwards:

  • Report summary: all images aligned, reprojection RMS below about 1 px, no quality flags.
  • dtm.tif and ground_support.tif: where the terrain is observed and where it is interpolated under the canopy.
  • chm.tif gives tree heights; they are correct even though the absolute heights of a non-RTK drone can be tens of metres off (Section 8.3).
Tip. Start with --quality medium for a quick check of a new dataset, then branch the dense step at high quality (Section 14.6).

14.2 RTK drone with N2000 heights

A DJI RTK drone with fixed solutions (RtkFlag 50) over Finland. Its heights are ellipsoidal; the outputs should be in N2000 and labelled so.

photogrammetry -i images -o project --preset drone,city --quality high \
  --gps-sigma 0.05 \
  --target-geoid /data/geoid/fin2005n00.gtx --crs EPSG:3067+3900 \
  --orthomosaic
  • --gps-sigma 0.05 tells the GPS-weighted adjustment that the positions are accurate to centimetres.
  • Check 07_results/coordinates.json: vertical_crs is EPSG:3900 and vertical_conversion shows the height shift applied (about −17 to −20 m in Finland).

14.3 Survey with ground control points

Ten surveyed points in ETRS-TM35FIN with N2000 heights; two held back as check points automatically.

# 1. Process up to the gcp step; it stops as 'waiting'
photogrammetry -i images -o project --preset drone,city --quality high \
  --gcp gcps.csv --gcp-check auto --crs EPSG:3067+3900

# 2. Pin the points in the images; Done continues the run (gcp, dense, finish)
photogrammetry gcp-edit -o project

In the report, the control point residuals show how well the block fits the points, and the check point residuals give the independent accuracy. GCP heights are used as given, so the +3900 label is correct without a geoid conversion.

On a server without a display, pin the markers in the local web page instead and continue by hand:

photogrammetry gcp-edit -o project --browser      # open http://127.0.0.1:8765, press Done
photogrammetry gcp dense finish -o project

14.4 Georeferencing to national lidar

A forest survey without GCPs, tied to national airborne laser scanning (a folder of LAZ tiles in ETRS-TM35FIN, N2000).

photogrammetry -i images -o project --preset drone,forest --quality high \
  --lidar-reference /data/als/tiles --lidar-vertical-datum N2000 \
  --crs EPSG:3067+3900 --classify-ground
  • Check the coverage before processing with Check lidar coverage in the window; the step stops if the tiles do not cover the block plus 10 m.
  • The report's Lidar Reference page lists the estimated shifts and angles with their standard deviations, the parameters left at the GPS values, and maps of the differences to the lidar.
  • If the lidar is several years old, canopy has changed: the default canopy weight (0.1) already relies mostly on open ground and roofs.

14.5 Aerial block with imported orientations

A large-format aerial block with exterior orientations from an INPHO project in ETRS-TM35FIN. The orientations are trusted; POSE only makes the dense products.

photogrammetry -i /data/block/images -o /data/block/project \
  --orientation-input /data/block/block.prj --orientation-crs EPSG:3067 \
  --preset aircraft --quality medium \
  --memory-mb 50000 --mvsgm-cameras-in-flight auto

If the INPHO heights are ellipsoidal, add --target-geoid fin2005n00.gtx --crs EPSG:3067+3900; if they are already N2000, add only --crs EPSG:3067+3900. If the pixel size is missing from the project file, give it with --orientation-pixel-size MM.

14.6 Comparing settings with branches

Align once, then try several dense settings on the same alignment:

# Alignment and georeferencing only
photogrammetry inputs calibrate match align georeference -i images -o project \
  --preset drone,forest --quality high

# Three dense variants, each in its own run (RUN = the run above)
photogrammetry dense finish -o project --run RUN --branch --min-views 2
photogrammetry dense finish -o project --run RUN --branch --min-views 3
photogrammetry dense finish -o project --run RUN --branch --filtering moderate

# Which steps each run has done
photogrammetry status -o project --run RUN

Each branch writes its own 07_results; compare the reports, the point counts on the Project tab, or the clouds in the 3D view.

14.7 Large block on a server

A few thousand images on a Linux server under Slurm. The job script sets a memory budget below the job's limit, keeps a log, and uses dense checkpoints so a killed job can continue.

#!/bin/bash
#SBATCH --mem=180G --cpus-per-task=32 --gres=gpu:1 --time=48:00:00
POSE=/opt/pose/pose.sh
OUT=/scratch/$USER/block-project

$POSE -i /scratch/$USER/images -o $OUT \
  --preset aircraft --quality high \
  --cores 32 --memory-mb 100000 --ram-limit-mb 175000 \
  --descriptor-matcher flann --calibration-trial-method subset \
  --mvsgm-cameras-in-flight 4 --dense-checkpoint 30 \
  > $OUT.log 2>&1

If the job stops during the dense step, find the run ID in the log and continue it:

$POSE status -o $OUT
$POSE dense finish -o $OUT --run RUN_ID --memory-mb 100000

The run continues after its last checkpoint with the same result as an uninterrupted one. With very large sets, --block-processing auto splits the block by GPS position instead (Section 11.5).

14.8 Exports and later products

photogrammetry --export-orientations project/runs/RUN_ID --orientation-output-format colmap,metashape,csv

# The report again, with full diagnostics
photogrammetry --export-report project/runs/RUN_ID --report-detail full

BFile formats and conventions

B.1 Camera convention

X_camera = R * X_world + t
C_world  = -transpose(R) * t
camera axes: x right, y down, z forward
pixel (0,0) = centre of the upper-left pixel

gcp_id,x,y,z,sx,sy,sz,type

Header optional; separator comma, semicolon or tab. Coordinates in --crs, sigmas in metres (optional), type control or check (default control).

image,camera
DJI_0001.JPG,rgb
DJI_0002.JPG,nir

B.4 Poses (native CSV)

image,r00,r01,r02,r10,r11,r12,r20,r21,r22,tx,ty,tz

image,width,height,fx,fy,cx,cy,k1,k2,p1,p2,k3

B.6 Geoid grids

NOAA/PROJ .gtx (binary: big-endian south-west latitude and longitude, latitude and longitude spacing as doubles, rows and columns as integers, then rows of 32-bit floats from the south; -88.8888 marks a missing node), or text:

# latitude longitude N
59.00  19.00  16.3821
59.00  19.50  16.5130
...

Degrees and metres, one node per line, a regular grid, latitude first. Lines that are not numbers are skipped.

B.7 coordinates.json

Describes the output frame: horizontal_crs and epsg, vertical_crs (e.g. EPSG:3900, or null), vertical_datum, height_note, the GPS fit (inlier_rms_metres, gps_inliers), and with a height conversion vertical_conversion (source, target, height shift). GCP- and lidar-referenced runs say so in datum.
