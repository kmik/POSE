About this manual

This manual describes how to use POSE: installing it, processing photographs into point clouds, surface and terrain models and orthomosaics, controlling the georeferencing and heights, and checking the quality of the results. Chapters 1 to 3 are enough to make a first point cloud. Chapters 4 to 13 explain each part of the processing in turn. Appendix A lists every command-line option, generated from the program's own help text, so it always matches the version it was made with.

Conventions used here:

  • photogrammetry stands for the launcher of your system: photogrammetry.bat or pose.bat on Windows, photogrammetry.sh or pose.sh on Linux.
  • PROJECT is a project folder, IMAGES a folder of photographs and RUN the folder of one run inside a project (PROJECT/runs/<run-id>).
  • Options are written --option VALUE; --option=VALUE works too.
  • Pixel values refer to the processed images (after any resizing), unless stated otherwise.
Draft. This is the first draft of the manual. Sections marked with figures to come, and the details of some advanced options, will be filled in during revision.

1Introduction

1.1 What POSE does

POSE (Photogrammetric Orientation and Surface Estimation) turns overlapping photographs into georeferenced 3D products. It finds the position and orientation of every camera, calibrates the lens, matches the images densely and fuses the depth maps into a point cloud. From the cloud it makes a surface model, a terrain and canopy height model, and an orthomosaic. A PDF report documents every run.

POSE is written in Java and uses OpenCL to run dense matching and depth fusion on a graphics card. Without a suitable GPU everything runs on the CPU, with the same results. It runs from the command line, in a desktop window, or as part of the LAS.utils toolkit.

Typical uses are drone and aircraft surveys of forests, built areas and terrain. POSE was developed with forest inventory in mind: it handles canopy, keeps thin structures, and can tie a block to existing airborne laser scanning instead of ground control points.

1.2 The processing chain

Processing runs as a chain of steps. Each step saves its result, so the chain can be run in one go or step by step.

StepWhat it doesMain result
inputsReads the photographs and their metadata, plans the processing resolution and memory, imports supplied orientations.Image inventory, resolution plan
calibrateSets up the cameras: supplied calibration, calibration from EXIF, or automatic estimation.Camera groups, initial calibration
matchDetects features, chooses the image pairs to match, matches them and builds tie-point tracks.Tie points
alignRegisters the cameras one by one and refines everything with bundle adjustment, including the lens.Camera poses, sparse cloud
cleanupOptional: removes weak tie points and adjusts again.Cleaned tie points
georeferenceMoves the block into map coordinates using the image GPS, then a GPS-weighted adjustment.Georeferenced cameras
lidarOptional: fits the block onto an airborne lidar surface.Lidar-referenced cameras
gcpOptional: adjusts the block to ground control points pinned in the images.GCP-referenced cameras
denseDense matching and depth fusion.Dense point cloud
groundOptional: ground classification, terrain and canopy height models.DTM, CHM, classified cloud
finishSurface model, optional orthomosaic, processing report, final files.DSM, orthomosaic, report

1.3 What you get

  • Point cloud: dense.las (LAS with RGB and optional per-point values) and dense.ply.
  • Surface model: dsm.tif, a GeoTIFF of the highest point per cell.
  • Terrain and canopy (with ground classification): dtm.tif, chm.tif and ground classes in the LAS.
  • Orthomosaic (on request): orthomosaic.tif, a full-resolution tiled GeoTIFF.
  • Processing report: processing-report.pdf with survey data, calibration, camera positions, accuracy and quality flags.
  • Camera orientations: calibration and poses, exportable to other software (COLMAP, Metashape, INPHO and others).

1.4 Projects, runs and steps

A project is a folder that holds everything made from one set of photographs. Each time you process, POSE creates a new run inside it, in PROJECT/runs/<run-id>. Runs are never overwritten: changing a setting and processing again gives a new run next to the old one, so results can be compared. A run consists of the steps listed above. A step can be continued later, and a run can be branched: a new run starts from the saved state of an earlier one and redoes the steps from a chosen point with other settings. Chapter 5 explains this in detail.

1.5 Requirements

  • Operating system: Windows x64 or Linux x64 (glibc 2.28 or later for the portable Linux package).
  • Java: a 64-bit Java 25 runtime. Portable packages include it; a source build needs a JDK 25.
  • GPU (optional): a graphics card with a vendor OpenCL driver (NVIDIA, AMD or Intel). Double-precision support lets fusion run on the GPU too.
  • Memory: 16 GB of RAM is enough for small drone projects; large blocks or high resolution need 64 GB or more. Chapter 11 explains how memory is planned.
  • Disk: plan for several times the size of the photographs for temporary depth maps and caches; dense matching at full resolution of large blocks can need hundreds of gigabytes.

2Installation

2.1 Portable release

The portable release is the easiest way to run POSE. It contains the compiled program, its libraries and a private Java runtime. Nothing is installed into the system and no administrator rights are needed. Download the release archive (not the source archive generated by GitHub), check it and extract it:

# Linux
sha256sum -c pose-VERSION-linux-x64-glibc228.tar.gz.sha256
tar -xzf pose-VERSION-linux-x64-glibc228.tar.gz
cd pose-VERSION-linux-x64-glibc228
./pose.sh -h

On Windows, extract the Windows package and run pose.bat -h. The folder can be moved and its path may contain spaces. Input and output paths are relative to the folder you start POSE from, not to the installation.

The bundled runtime is used even if another Java is installed. To use a different Java 25 for a single command, set POSE_JAVA_HOME for that command.

2.2 Building from source

Building needs a 64-bit JDK 25. The first build downloads the libraries into lib/, compiles the program and runs its test suite.

# Windows
.\build.bat
.\photogrammetry.bat -h

# Linux
bash build.sh
bash photogrammetry.sh -h

The test suite takes a while. When it passes, the program is ready. To use POSE inside LAS.utils, copy the repository into sgm_java/ at the LAS.utils root, copy the wrappers from las-utils/ into that root and build the module.

2.3 GPU (OpenCL)

GPU processing needs a working graphics driver with OpenCL; POSE does not install it. Check what POSE sees with:

photogrammetry --list-gpus

The list numbers the devices from 0. Choose one with --gpu-device N. By default (--compute auto) POSE uses the GPU where it is worthwhile and fits in its memory, and falls back to the CPU otherwise. --compute cpu never touches the GPU; --compute gpu makes a missing GPU an error.

Tip. On a laptop with two graphics adapters, make sure the discrete GPU is the one listed as device 0, or pick it with --gpu-device.

2.4 Launchers and Java memory

LauncherStarts
photogrammetry.bat, photogrammetry.shThe command-line program.
pose.bat, pose.shThe same program (shorter name).
pose-gui.bat, pose-gui.shThe desktop window (Chapter 4).

The launcher starts Java with an initial heap of 8 GB (environment variable PHOTOGRAMMETRY_HEAP, e.g. 16g). You rarely need to change it: --memory-mb restarts the program with a heap large enough for the requested processing budget (Chapter 11).

3Quick start

You need a folder of overlapping photographs. For drone surveys, typical overlaps are 70–80% along the flight line and 60–70% between lines; forests need more overlap than open ground. Photographs with GPS in the EXIF are georeferenced automatically.

3.1 In the window

  1. Start pose-gui.bat (Windows) or ./pose-gui.sh (Linux).
  2. Choose a project folder at the top. A new, empty folder is fine.
  3. On the New run tab, choose the image folder.
  4. Pick a Preset, for example drone, forest or drone, city, and if needed tick Classify ground and Orthomosaic.
  5. Press Run. The console shows the steps, a progress bar and the log.
  6. When the run completes, press Open to see the report or the results folder.

The window fills in the CPU, memory and GPU settings for your computer. Its defaults are the tested multi-view setup (Chapter 9), which differs from the command-line defaults.

3.2 On the command line

photogrammetry -i IMAGES -o PROJECT --preset drone,forest --classify-ground --orthomosaic

This runs every step in one process. A smaller and faster first test:

photogrammetry -i IMAGES -o PROJECT --quality medium

To see the memory plan without processing:

photogrammetry -i IMAGES -o PROJECT --quality high --estimate-memory

Help on all options: photogrammetry -h. Only the options that mention a word: photogrammetry --help lidar. Chapter 14 has complete command sequences for common kinds of survey.

3.3 Where the results are

Results are in PROJECT/runs/<run-id>/07_results/:

FileContents
dense.las, dense.plyDense point cloud.
dsm.tif (+ .tfw, .png, .json)Surface model, when the run is georeferenced.
dtm.tif, chm.tif, ground.jsonTerrain and canopy height (with --classify-ground).
orthomosaic.tifOrthomosaic (with --orthomosaic).
processing-report.pdfProcessing report.
coordinates.jsonCoordinate system and height datum of the outputs.
report.txtShort text summary.

PROJECT/latest-files.csv lists the outputs of the newest successful run.

4The POSE window

The POSE window starts runs, follows them and inspects their results. It does not process anything itself: every command it starts is the normal command line, shown in the console so that it can be copied and run elsewhere, for example on a server.

4.1 Starting and layout

pose-gui.bat [PROJECT]          (Windows; no console window)
./pose-gui.sh [PROJECT]         (Linux)
photogrammetry gui [PROJECT]    (any launcher)

The window has a project folder bar at the top, the tabs New run, Advanced options and Project, and a console at the bottom. The window needs a display; on a machine without one, use the command line. On Windows, set POSE_GUI_CONSOLE=1 before pose-gui.bat to keep a console window for error messages.

The console shows the steps of the current run (pending, running, complete, skipped, waiting, failed) with their times, the current stage with its percentage, the live log, the elapsed time and a Stop button. Stop ends the command and every process it started; the stopped step stays marked "running" and can be run again from the Project tab. Only one command runs at a time.

4.2 New run

  • Input and project: image folder; optional orientation import, GCP file and check points; optional lidar reference (one LAS/LAZ file or a folder of tiles) with its main settings; coordinate system and height datums. Check lidar coverage tests at once whether the lidar covers the photographs.
  • Processing: the Preset menu, then quality, maximum image dimension, dense method, filtering, minimum views, quick calibration, tie-point cleanup, ground classification and orthomosaic.
  • Compute and memory: compute device, GPU index and memory, GPU normals, CPU cores, memory budget and RAM limit.
  • Outputs: PLY on/off, LAS tile size, point confidence file, the per-point values stored in LAS/PLY, verbose log.

Hover over a label to see the option's help text. An empty field is not passed, so the default applies; the default is shown in grey. Extra arguments takes options typed by hand; they come last and win. The Command box shows the exact command and whether the option parser accepts it. Memory estimate runs --estimate-memory in a temporary project. Run starts the run; Reset options returns all options to the window's defaults.

The window's own defaults are the tested multi-view setup. The compute sizes come from the computer: three quarters of the CPU cores, half the RAM for --memory-mb, and 95% of GPU memory. Choosing mvsgm as the dense method brings its required and tested settings with it. Options are remembered per project folder, and the last options used become the defaults for new projects.

4.3 Advanced options

Every other option (about 250) has a field on the Advanced options tab, grouped as in Appendix A. The fields are made from the program's help text, so they always match the program. Search filters by name or help text; Show only the options I set lists your changes, and the tab title counts them.

4.4 Project tab

  • Runs of the project with start time, status, number of points and the next step.
  • Steps of the selected run, with buttons to Run next step, Run remaining steps or Run selected steps, and Redo steps in a new run..., which branches the run (Section 5.2). Options for these steps passes options to the steps run here.
  • Edit GCPs when a run waits for ground control markers; Clean tie points... when it waits at the cleanup step.
  • Report again and Orthomosaic again remake these products without reprocessing.
  • Summary and quality flags: the main numbers of the report and its flags. Copy run details copies the run's status, error and log end for a bug report; Copy command copies its options as one command line.
  • Double-click a step for its full message; a failed step shows the error and the relevant log lines.

4.5 3D view, Images, tie points, lidar and registration windows

3D view... shows the dense cloud, tie points and cameras of the selected run. Colour by RGB, height, class, surface attributes or point confidence. Cameras flagged by camera screening are drawn red. Left drag orbits, right drag pans, the wheel zooms to the pointer and double-click centres. Home, Top and Side set standard views; Shading adds eye-dome lighting. For runs with a lidar reference, the lidar points can be shown in orange for direct comparison.

Images... shows the photographs with their reprojection error and flags, at full resolution on the Image tab and projected onto the surface model on the Map tab. With lowered opacity, well-aligned overlapping photographs look sharp and misaligned ones look doubled.

Tie-point cleanup (Section 7.5) shows histograms of the tie points' error, views and angle with a 3D view of what the chosen limits remove. Lidar result... shows the lidar step's coverage, transformation and difference maps. Registration... shows how each image was registered or why it was not, with the matched pairs on a map.

The GCP marker editor is described in Section 8.4.

4.6 Settings and help

Settings > Preferences sets the interface scale, whether new projects start with the last or the default options, whether the report opens when a run completes, and the size of the image preview cache. Fit compute options to this computer resets cores, memory and GPU memory from the hardware. Settings are kept in %APPDATA%\POSE\gui (Windows) or ~/.config/pose/gui (Linux).

The Help menu has the user guide (F1), the searchable command-line options and About POSE with version and system details.

5Projects, runs and steps

5.1 The steps

Without step names, POSE runs every step in one process:

photogrammetry -i IMAGES -o PROJECT [options]

With step names it runs only those steps, in order. inputs starts a new run and needs -i; the other steps continue the newest run with the options saved by inputs. Options given to a later step are added to the saved ones and override them.

photogrammetry inputs -i IMAGES -o PROJECT --quality medium
photogrammetry calibrate match align georeference -o PROJECT
photogrammetry dense ground finish -o PROJECT --min-views 2 --classify-ground

The optional steps cleanup, lidar, gcp and ground run only when their options are given; otherwise they are marked skipped and need not be named. Two steps can stop as waiting: gcp until enough markers are pinned, and cleanup with --tie-point-cleanup pause until the limits are chosen in the window.

Show the state of a run:

photogrammetry status -o PROJECT [--run ID]

5.2 Continuing and branching runs

--run ID continues a given run instead of the newest one. --branch starts a new run from that run's saved state just before the first named step and redoes the steps from there; the source run is not changed:

photogrammetry dense ground finish -o PROJECT --run ID --branch --min-views 2

Options only change the steps that use them. For example --features belongs to match, so to change it, branch from match. Options that would invalidate the saved state of earlier steps are refused; the message says which step to branch from instead.

Tip. Branching is the quick way to compare settings: align once, then branch the dense step several times with different dense options.

5.3 Interruptions and checkpoints

Each step saves its state when it completes. If a run is interrupted, run the interrupted step again on the same run (--run ID); the completed steps are not repeated.

The dense step of a multi-view run can take hours. It saves a checkpoint every 30 minutes by default (--dense-checkpoint auto, or a number of minutes). After a crash or a killed job, run the same dense command on the same run:

photogrammetry dense finish -o PROJECT --run ID

It continues after the last checkpoint and gives the same result as an uninterrupted run. The progress bar starts at 0% and jumps forward when the first camera after the checkpoint is done. Resource options such as --cores, --memory-mb, --gpu-memory-mb and --mvsgm-cameras-in-flight may change on resume; other options must stay the same, otherwise the dense step starts over.

5.4 Running on a server

On a server without a display, use the command line. A convenient workflow is to set up and test a run in the window on a desktop computer, use Copy command on the Project tab, and run that command on the server with its paths adjusted. Ground control markers can be pinned on the server with gcp-edit --browser, which serves a local web page.

Under a job scheduler (for example Slurm), request somewhat more memory than --memory-mb: the Java heap is about --memory-mb/0.65 and native memory comes on top (Section 11.1). --ram-limit-mb tells POSE the job's memory limit when it cannot detect it. Write logs to a file and keep the run ID: an interrupted dense step resumes from its checkpoint.
