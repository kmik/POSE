# GPU port of per-pair dense stages, 10 November 2026

Rule for every piece: default output byte-identical to a reference run of the previous code on
city2 (17 images); each GPU path has a CPU fallback with the same
results and checks itself against the CPU code on first use; device memory per pair is bounded and
reserved from the shared pair-worker pool (`GpuMemoryPool`).

## Identity check and the LAS header date

`dense.las` stores the file creation day of year in its header (bytes 91-94). Runs made after
midnight on 10 November therefore have a different LAS SHA-256 (`b04c3faf…` instead of
`4bea0409…`) with byte-identical point records; the baseline classes give the same `b04c3faf…`
today. Such a file counts as identical when `cmp` against the reference LAS shows that only
those header bytes differ. PLY and
`point-confidence.bin` have no date and are compared by hash.

## Piece 1: edge-aware depth outlier filter on the GPU (done)

`GpuDepthOutlier` (new) decides `DepthOutlierFilter` codes on the GPU; `DepthOutlierFilter.mask`
uses it and falls back to the unchanged parallel CPU loop (`DepthOutlierFilter.codes`).

- The kernel is `DepthOutlierFilter.decision` in FP64 with the same operation order, no FMA
  contraction (`#pragma OPENCL FP_CONTRACT OFF`), correctly rounded division and sqrt (OpenCL FP64
  requires both), Java `Math.max/min` semantics, and the same RANSAC trial indices and early exits.
  The median of the residuals is the same order statistic (insertion sort instead of `Arrays.sort`).
- Pixels that reach `structure()` (Math.hypot/atan2/sin/cos) come back with code 255 and are
  decided by the Java code. On city2 that is 22 of 2.25 M pixels per pair.
- Speed: consumer GPUs run FP64 at 1/64 of the FP32 rate, and the RANSAC support counting is
  about 2,300 residual tests per pixel. Each test `|z - a x - b y - c| <= tolerance` is first done
  in float with a margin of 32 float ulps of the magnitudes involved (the float and double
  evaluations both differ from the exact value by less than about 7 ulps). Only tests within the
  margin of the tolerance (and NaN/overflow cases) evaluate the double expression, so every
  decision equals the double comparison. This took the kernel path from 325 ms to 113 ms on a
  2.25 Mpx raster (16 CPU threads: 0.9-1.0 s).
- Applies when `--compute` is not `cpu`, the strip has at least 250,000 pixels, the radius is at
  most 5 (default 3; the option allows up to 8) and pool memory can be had; otherwise the CPU
  code runs. `-Dsgm.cpuDepthOutlier=true` forces the CPU.
- Self-check: the first use in a process recomputes every eighth row on the CPU and compares all
  codes; a difference (or any GPU error) prints a warning, disables the GPU path for the process
  and returns the CPU result. city2 log line: `GPU depth outlier filter: 250 sampled rows (83845
  decisions) identical to the CPU code; 22 of 2250000 pixels returned to the CPU`.
- Memory: about 10 bytes per pixel (depth, gray, left/right error, codes), reserved with the new
  `GpuMemoryPool.reserveAuxiliary`. It waits for pool memory only when the calling thread holds no
  pool memory; a thread that holds some (a banded session) takes the bytes only if they are free
  now, otherwise it uses the CPU. So the filter cannot deadlock against banded sessions.

Measured, city2 dense step as a branch of the reference run (6.2 GB heap, 3 pairs in flight), current then
baseline classes back to back:

| | baseline | piece 1 |
|---|---:|---:|
| 05 stereo stage | 55.3 s | 49.2 s |
| 06 fusion stage | 38.5 s | 37.3 s (not affected; run-to-run variation) |
| outlier filter, sum over 58 pairs | 14.9 s | 4.9 s |
| CPU profile samples in the filter (earlier JFR run) | 3,384 | not measured |
| dense.las / dense.ply / point-confidence.bin | SAME / SAME / SAME | SAME / SAME / SAME |

The filter's wall time per pair is now 0.04-0.6 s depending on how busy the GPU is with the
other pairs' SGM; most of the gain is CPU time freed for the other pair workers.

Verification:
- Synthetic full-raster comparison, 1500x900, radii 2-5, with/without left/right error, three
  noise levels, outliers, blobs, a thin line, holes and a partial core strip: 61.2 M decisions,
  0 differences (codes 2, 3, 5, 6, 7, 8, 9, 10 all exercised).
- New `GpuDepthOutlierRegression` in `SelfTest` (smaller version of the above, plus the pool
  rule); existing `DepthOutlierRegression` passes through the GPU path.
- city2 dense branch: 4 runs, all outputs identical.

## Piece 2: disparity-range estimate (done; identical ranges, no narrowing possible)

The estimate (`DisparityRange.estimate`) is: 640 px SIFT preview and reciprocal matching, then a
whole-domain coarse probe (`guard`: a 72x128 or 128x72 full-range census SGM, then ZNCC checks at
full resolution), then the union of the keypoint interval and the combined-evidence interval.
Profile of the baseline (CPU samples in the range estimate): about 70% in the probe's SGM, which
ran on the CPU (`PagedVolume.get`, `CensusSgm.match`, `StereoCost.hamming`) because its volume
(about 0.66 M cells) is below the 1 M cells at which `--compute auto` uses the GPU; about 25% in
the SIFT preview and its matching. Waiting on the shared SIFT lock was only about 1.3 s per run.

Change: the probe solve now runs on the existing full-range GPU SGM (`GpuSgm`/`GpuStereo`), which
gives the same disparities and statistics as the CPU `match` (checked here on 40 + 12 probe-sized
cases, bit for bit, plus the earlier GPU validation). Nothing in the range logic changed, so every
pair's search range, its samples and the TSGM seeds are exactly the same as before; no range can
be narrower.

- `Options.gpuSmallSolves` (package-private, not a CLI option, not part of run settings or cache
  keys) lets `GpuSgm.use` accept volumes under 1 M cells; only `DisparityRange.guardSolve` sets it.
  The per-solve "GPU SGM storage" console line is not printed for these solves.
- Fallbacks: `--compute cpu`, `-Dsgm.cpuRangeGuard=true`, a GPU error (`GpuSgm.match` already
  falls back to the CPU `match`), or pool memory not available without waiting while holding some
  (`reserveAuxiliary`, about 3 MB) all run the CPU solve.
- Self-check: the first GPU probe in a process is also solved on the CPU and compared (all
  disparity bits and the statistics); a difference prints a warning, disables the GPU probe for
  the process and the CPU result is used. city2 log: `GPU disparity-range probe: 72x128 solve
  identical to the CPU solve (3396 valid pixels)`.

Measured (city2 dense branch, back to back, baseline classes then pieces 1+2):

| | baseline | pieces 1+2 |
|---|---:|---:|
| probe SGM, sum over pairs | 12.4-13.8 s (CPU) | 1.4 s (GPU) + 2.5 s for the first-use checks |
| range estimate, sum over 58 pairs | 27.1-29.6 s | 19.6-21.3 s |
| 05 stereo stage | 58.8 s (55.1-55.3 s in two other runs) | 49.5 s (piece 1 alone: 49.2 s) |
| 06 fusion stage | 40.0 s | 36.9 s |
| dense.las / dense.ply / point-confidence.bin | SAME | SAME |

The stereo stage barely moved beyond piece 1: the freed CPU time in the range estimate is not on
the critical path with 3 pairs in flight (TSGM planning and the GPU solves are). What remains in
the range estimate (~0.33 s per pair) is the SIFT preview, its matching and the full-resolution
ZNCC checks. Their results are the range samples and TSGM seeds, so changing them (fewer
features, a different detector) would change results; left as is.

Tests: new `GpuRangeGuardRegression` (12 probes, bitwise) in `SelfTest`; `PairRangeRegression`
passes.

## Piece 3: TSGM coarse pyramid levels (done)

Baseline profile of `TsgmSearch.plan` (CPU samples): `derive`/`extremes` (windowed min/max of the
parent level's checked disparities for radii 1, 4, 16 and 64, then the bands) 43%, banded solves
22% (GPU, except the smallest coarse levels, which `--compute auto` sent to the CPU reference
`cpuSummary` below 200,000 cells), seeding/histogram/clamping at full resolution about 19%, 2x2
downsampling 4%.

Changes:

- `GpuTsgm` (new): `rows` and `columns` kernels compute the four windowed extremes of the parent
  map (direct window scans; minimum and maximum of a set of floats are exact in any order), and
  a `derive` kernel computes each pixel's band with the same float/int arithmetic as
  `TsgmSearch.derive`. Signed zeros cannot change a band (it uses floor(2 min) and ceil(2 max)).
  `TsgmSearch.derive` uses it for radius 1 (the only radius used) and falls back to the unchanged
  CPU code (`deriveCpu`). It applies to levels of at least 100,000 pixels when `--compute` is not
  `cpu`; `-Dsgm.cpuTsgmPlan=true` forces the CPU. Device memory: about 44 bytes per parent pixel
  plus 9 per pixel (city2 level 0: about 25 MB plus 20 MB), reserved with `reserveAuxiliary`.
- Small coarse banded solves use `GpuBandedStereo` too: the level options carry
  `gpuSmallSolves`, and `GpuBandedStereo.use` then accepts volumes under 200,000 cells. Larger
  coarse solves and the full-resolution solve are unchanged.
- Self-checks: the first GPU derive in a process is compared with `deriveCpu` on the whole level
  (low, count and the full-range count); the first small GPU banded solve is compared with
  `cpuSummary` (`BandedSgm.Pair.verifySmall`, all summary integers). A difference disables that
  GPU path for the process and the CPU result is used. city2 log:
  `GPU TSGM band planning: 281x500 level identical to the CPU derive`,
  `GPU banded SGM: small coarse-level solve (140x250, 195232 cells) identical to the CPU reference`.

Measured (city2 dense branch, back to back; this time with a larger heap, 4 pairs in flight):

| | baseline | pieces 1+2+3 |
|---|---:|---:|
| 05 stereo stage | 47.2 s | 37.7 s |
| 06 fusion stage | 30.5 s | 31.1 s (unchanged code) |
| TSGM planning, sum over 54 pairs | 33.2 s | 23.4 s |
| range estimate, sum over 58 pairs | 32.1 s | 22.3 s |
| outlier filter, sum over 58 pairs | 13.8 s | 4.3 s |
| wall (dense step incl. start-up) | 84 s | 75 s |
| dense.las / dense.ply / point-confidence.bin | SAME | SAME |

Tests: new `GpuTsgmRegression` in `SelfTest` (8 parent maps x 2 directions with holes needing every
fallback radius, an empty parent, signed minimum disparities, -0.0/+0.0 parents; 4 small banded
solves x 2 directions through `BandedSgm.Pair`). Note: the one-shot `GpuBandedStereo.summary(...,
reverse=true, ...)` expects the images already swapped; production code goes through
`BandedSgm.Pair` and is unaffected.

Left in TSGM planning: seeding, band histograms and image clamping at full resolution, the 2x2
downsampling and the per-level census on the CPU (exact ports would be simple but are about 20%
of the remaining planning CPU time), and the session set-up per coarse level (uploads; one
session per level).

## Piece 4: triangulation and depth evidence (analysed; not ported, no wall-time gain available)

Profile of the current code (city2 dense branch, JFR, CPU samples at ~10 ms):

- `triangulateRow` (pair worker, 16 parallel row tasks): ~690 samples, about 7 CPU-seconds per
  run, 0.12 CPU-s or ~10 ms wall per pair. 35% is `StrictMath.asin` for the triangulation angle
  (fdlibm, not reproducible bit for bit on the GPU, and the angle is stored per candidate), the
  rest matrix products (`Math3.mv`) and array index checks. The projection arithmetic itself
  would be exact on the GPU, but moving it saves at most ~4 CPU-seconds per run.
- `publish` (coordinator thread, serial in pair order): ~1,120 samples (~11 s), almost all in
  `PagedVolume.get/set` and its page `HashMap` (`DepthFusion.addPlanned` -> `DepthRaster`), plus
  the candidate stream writes. This is ordered store work, not arithmetic; it must keep its order
  (the evidence store order is part of the identical output), so a GPU cannot take it over.
- Critical path: the pair threads' waits are all inside `compute` (GPU work); none waits for the
  coordinator, so `publish` overlaps the pair computation and is not on the critical path.

Decision: no GPU port (it could not reduce wall time measurably). If the coordinator becomes the
bottleneck later (more pairs in flight, faster pair compute), an exact CPU change would help more:
caching the last few pages per `DepthRaster` instead of one, which removes most `HashMap` lookups
without changing the store order.

## Fix: native SIFT crash (SIGSEGV in `SIFT_Impl::detectAndCompute`, Linux, 3,000+ images)

Cause: OpenCV's Java wrappers (4.9.0) delete their native object in `finalize()`, and
`Feature2D.detectAndCompute` reads the detector's native handle and then calls a static native
method with plain `long` handles. After that read the Java `SIFT` object is no longer reachable
for the JIT, so a garbage collection during detection can finalize it and delete the native
detector while it is still running (use-after-free; the crash jumps to address 0 inside
`detectAndCompute`). Long runs with many images (frequent GCs, several extractions at once) make
it likely; on Windows the same race showed up as the occasional "preview feature detection failed
(unknown exception); retrying it" in the range estimate.

Fix: `Reference.reachabilityFence(sift)` after the native calls in `ImageFrame.extract` (feature
extraction, where the Linux run crashed) and `DisparityRange.estimate` (preview SIFT). The
descriptor matchers were already safe (each is used again in a `finally`), and no other OpenCV
algorithm object or inline temporary `Mat` is passed to a native call without a later use.
Results are unchanged (only object lifetime): city2 whole-pipeline run with the fix gives the
same exterior.csv, PLY, confidence and LAS points. The preview retry warning appeared in 8 of 15
city2 runs before the fix and in 0 of 4 runs after it.
