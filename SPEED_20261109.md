# Throughput revision, 9 November 2026 (evening)

Every change below keeps the results **bit-identical**: on city2 (17 images, a 17-image urban
drone set with the settings below) `04_geometry/final/exterior.csv`, `dense.las`, `dense.ply` and
`point-confidence.bin` have the same SHA-256 as a reference run made with the previous code, both
for the step-by-step dense branch and for a single-call run of the whole pipeline. No option,
default output or file format changed.

## Results (city2, RTX 5070 laptop, `--cores 12`)

Whole pipeline in one call, pre-change classes then current classes, run back to back (both
with a ~6 GB heap, so 3 stereo pairs in flight in both):

| Stage | before (s) | after (s) |
|---|---:|---:|
| 01 calibration (focal bootstrap + refinement) | 30.4 | 24.9 |
| 02 features | 13.0 | 7.6 |
| 03 matches | 5.3 | 5.4 |
| 04 geometry (registration, bundle, GPS adjustment) | 39.5 | 37.4 |
| 05 stereo | 71.5 | 55.5 |
| 06 fusion | 44.9 | 37.4 |
| **wall, whole run** | **229** | **192** |

Dense step alone (branch from the reference run, `dense` step as in the step-by-step workflow, 8.9 GB heap):
stereo 75.1 -> 46.5-49.1 s, fusion 48.8 -> 34.9-36.7 s (4 pairs in flight; 3 pairs: stereo
55-57 s).

This is a 16-25% reduction, not the several-fold reduction needed to approach Metashape: the
remaining time is spread over many CPU stages that would have to move to the GPU or change
algorithmically (see "Not done").

Timings on this laptop vary by about 10% between runs, and the launcher sizes the heap from the
RAM that is free at start-up (5.9 to 8.9 GB in these runs), which changes how many stereo pairs
run at once.

## What changed

### Dense matching (05_stereo)

- **Shared GPU memory for concurrent pairs** (`GpuMemoryPool`). Each pair worker used to get a
  fixed 1/N share of the GPU budget; a pair whose packed volume did not fit fell back to the CPU
  banded solve (identical result, ~100x slower; with 6 pairs in flight one pair took 97 s). Now
  every worker sees the whole budget and a banded session reserves its device bytes from a
  first-come-first-served pool before allocating. A session that must grow is closed and
  re-created rather than waiting while holding memory, so workers cannot deadlock.
- **Pairs in flight (auto)**: one per 3 cores (at most 6) instead of one per 4 (at most 4), when
  the existing conservative per-pair host-memory estimate fits the processing allowance;
  otherwise the former value. city2: 3 -> 4 pairs with an 8.9 GB heap, still 3 with 5.9 GB.
- Concurrent pair workers no longer halve their row workers (`--stereo-pipeline` halves them for
  the serial path's look-ahead preparation, which concurrent pairs do not use). Row tasks use
  four chunks per worker for balance.
- `GpuStereo.select` reads the GPU summary from a Java array instead of per-element
  `MemorySegment` reads (these were ~20% of the pair workers' time).
- Census descriptors: bits accumulated per 64-bit word without branches; texture mask with
  separable window extrema. TSGM band planning: column extrema over row-major blocks (no strided
  access), counter instead of a modulo per element, reused buffers.
- Edge-aware depth outlier filter: a departure within `--depth-outlier-deviation` is decided
  (code 5) without sorting the residuals; RANSAC support counts stop once a hypothesis cannot
  beat the best one; branch-free counting.
- Candidate stream: 4 MB buffer (8 KB writes dominated the serial publication step).
- Disparity-range preview SIFT: an OpenCV failure is retried in place (it happened in about
  one pair per run and made the coordinator recompute the whole pair serially). The preview
  matcher runs under the same lock as the detector.
- One reusable summary buffer per GPU banded session (54 MB per solve before).

### Fusion (06_fusion)

- Pass 1 (per-camera merge and filters) runs several cameras at once, bounded by heap (half of
  the remaining headroom; the pair cache keeps the rest). Each camera's pass 1 reads only its
  own pairs; counts are added in camera order.
- Splatting a camera's pairs runs the pairs concurrently (each pair has its own rasters, filled
  in candidate order).
- Output staging runs on one writer thread in camera order while the next camera is
  cross-checked; ownership marks are still applied before the next camera.
- Spike filter: a pixel within two footprints of the median is kept without the second sort.
- Camera votes: the band `3*hypot(hypot(a, b), f)` is bracketed with a 1e-12 relative margin;
  only votes inside that margin compute the exact hypot. Rounding is monotonic, so decisions
  are those of the exact band.
- Surface patch models: early termination of support counts; hull points sorted by packed
  integer keys (same order). Per-thread scratch for normal estimation.

### Calibration, features, bundle adjustment

- Feature extraction (calibration bootstrap and the match step) extracts up to 4 images at a
  time (OpenCV SIFT used 2-3 cores per image). Everything order-dependent (colours, exports,
  descriptor-cache accounting) stays in the ordered loop; a failed concurrent extraction is
  repeated serially.
- Bundle adjuster, shared-lens rows (13 parameters): lens normal accumulated from flat copies of
  the observations' lens Jacobians, upper triangle only and mirrored (each element receives the
  same products in the same order); point elimination and the right-hand-side scatter for the
  lens rows are partitioned by destination columns (each camera task also fills the lens rows'
  entries in its 6 columns, in point/edge order) instead of 13 tasks that each traversed every
  point and edge.

## Optional outputs and one-process runs (added later the same evening)

New options (defaults unchanged, so default runs write exactly the same files):

- `--ply off`: no `07_results/dense.ply` (283 MB on city2). The report DSM then reads
  `dense.las` (new LAS mode in `PlyStream`); ground classification already worked without the
  PLY; `--analyze-run` still needs it. `latest-files.csv` no longer points at an older run's PLY.
- `--point-confidence off`: no `07_results/point-confidence.bin` (1.0 GB on city2). Ignored, with
  a note, when ground classification/correction or `--diagnostics` is requested (they read it);
  the ground step warns if it is missing.

Measured on city2 with `--quick-calibration`, the step-by-step workflow
(`photogrammetry.bat`, eight processes, ~6 GB heap):

| | outputs on | `--ply off --point-confidence off` |
|---|---:|---:|
| dense step | 98 s | 98 s |
| finish step | 13 s | 13 s |
| whole run | 178 s | 178 s |
| files in 07_results | 1.57 GB | 0.29 GB |

Skipping the two files saves about 1.3 GB of disk but only about 1.5 s here (the results stage
went from 13.2 to 11.8 s); writing them was not the bottleneck on this machine. `dense.las` and
`exterior.csv` were identical in both runs.

What does save time is running the steps in one process: each separate step costs 2.5-4.5 s of
JVM/OpenCV start-up and state reload, about 20 s in total.

| city2, `--quick-calibration --ply off --point-confidence off` | wall |
|---|---:|
| eight separate step commands | 178 s |
| `inputs ...` then `calibrate match align georeference dense ground finish -o PROJECT` | 160 s |

Both give identical files; the second keeps the step-based project and run history.

## Not done (would change results; need a quality decision)

- Seeding calibration from the EXIF/XMP focal length instead of the three-start bootstrap
  (`--calibration-pipeline joint` exists but is experimental), reusing bootstrap features in the
  match step (different undistortion, so not identical), fewer GPS focal starts.
- Making PLY or the 1 GB `point-confidence.bin` optional (the ground step reads the latter).
- Porting the remaining per-pair CPU stages (range estimate, TSGM coarse levels, outlier filter,
  triangulation) and the fusion cross-check to OpenCL with bit-exact double arithmetic.

## Notes

- One step-by-step run spent ~25 s with almost no CPU after the dense step had written
  its clouds; it did not reproduce in 15 benchmark runs (2 s there). It looks like I/O
  (antivirus scanning the new 1.5 GB of files is a likely cause); excluding the project output
  folder from real-time scanning would show it.
- Running the steps in one call (`photogrammetry -i ... -o ...` with all options) gives the same
  files and avoids eight JVM starts, state reloads and image decodes.
